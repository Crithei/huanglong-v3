## 和第二版相比的取舍

- **浏览器内编辑器没有移植。** 第二版允许任何人在页面里编辑卡片、导出整份 HTML、按页导入导出 JSON。本骨架改为在 `src/data/` 里改内容，再用 Git 合并，或者把数据文件发给汇总的人。卡片字段与第二版一致，所以以后补编辑器时不用改数据结构。
- **作品网址配置保留了**，只是从页面表单改成了数据文件里的 `url` 字段，校验规则相同（只接受 http/https）。
- **单文件分享保留了**，改由 `build-single.py` 生成。
- 第二版的游览页卡片（`tour-*`）和我的页的护照、想去、行程卡片，在设计稿里已被真实功能取代（攻略面板、设施列表、路线、印章墙、收藏列表），所以没有保留。

## 需要你决定的事

1. **要不要补回浏览器内编辑器。** 如果内容组的同学不方便改文件，可以加一个只在 `?edit` 下出现的编辑模块：改卡片、填网址，然后导出 `cards.js`，交给开发者放回仓库。这样仍然只有一份数据来源。
2. **技术路线。** 目标是微信小程序。现在的结构（数据和渲染分开、动作集中登记）迁移到小程序或 uni-app / Taro 时，数据和大部分逻辑可以直接搬过去，页面模板需要重写。什么时候切换，取决于什么时候需要真机能力（定位、登录、支付）。
3. **地图服务。** 已定为腾讯地图（2026-11-02）。网页端底图已接入；下一步是 WebService 代理（搜地点、景区外步行 / 驾车路线），Key 只放服务端。小程序端以后改用 `map` 组件。
4. **实景照片（2026-11-02 更新）。** 14 站中 13 站已有 Wikimedia Commons 上 CC BY / CC BY-SA 协议的实景照片，作者与原图链接见 README「素材授权」；黄龙洞仍是示意图。照片多为 2011 年前后拍摄，正式上线前最好换成景区授权或自己拍摄的近期照片。

## 已知问题

- 数字人：没有限流和问答日志（依赖云端额度）；模型偶尔不附命令或选错条件，命令只是提议，游客确认后才生效；没有语音朗读（交接包有，暂未搬）。

- 水滴四章：真机触控、低端手机 GPU 性能、微信内置浏览器里的 WebGL 都还没测；「减少动态效果」模式下的「查看下一状态」按钮沿用 v1 逻辑，本次没有在该模式下实测。
- 水滴四章的章节—景点对应写在 `vendor/huanglong-water/follow-state.js`，要改需在 v1 改好再复制（见该目录 README）。

- 地图在横屏或很矮的窗口里会比较挤；产品以竖屏为主，暂不处理。
- 导游的减站建议改用游线规划（按「轻松」节奏重算），但规划本身的步行时间是整段估算，没有按站间距离和海拔细算。
- 4.5 小时的方案通常只能细看一两站，因为入沟步行估算就要两个多小时；需要实测数据确认是否偏保守。
